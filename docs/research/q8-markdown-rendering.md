# Research — Q8: Markdown parser and renderer

**Resolves:** [open-questions.md](../open-questions.md) Q-8 (blocks v0.1)
**Status:** Recommendation for the architecture phase. Not a decision until the leader records it in architecture.md.

---

## Question restated

medd needs to turn Markdown source into rendered HTML for the preview pane, live, on every keystroke that survives the debounce, without visible lag on ordinary documents and without falling over on large ones (N-3). The choice determines three other things at once: how faithfully GFM tables, task lists, footnotes and strikethrough render (R-1, R-5); how fenced code gets syntax-highlighted (R-3); and what the sanitisation story is for any raw HTML a Markdown file happens to contain. It also has to leave room for wikilinks, Mermaid, and math later without a rewrite, even though none of those ship in v0.1 (scope-mvp.md). Underneath all of that sits a placement question specific to this architecture: medd is Rust plus a WebView frontend (D-2), so "which parser" is inseparable from "which process runs it," because whatever runs on the Rust side has to get its output across the Tauri IPC bridge to be displayed.

## Options

### Rendering in Rust: pulldown-cmark

pulldown-cmark is the pull-parser most of the Rust ecosystem already depends on transitively (it's what mdBook and a large share of static-site generators use). Checked against its GitHub repo, it is genuinely active: last push 2026-09-11, latest tagged release v0.13.4 (2026-05-20), 92 open issues on a project of its size and age — a normal churn level, not neglect. crates.io lists 0.13.3 as the latest published version. It supports GFM tables, task lists, strikethrough, and footnotes, all opt-in via `Options` flags rather than always-on, which matters because it means CommonMark-only documents pay nothing for extensions they don't use. It does not build a full AST by default — it's an iterator over events — which is exactly the right shape for a custom HTML renderer that wants to intercept specific event kinds (a fenced-code-block-start event, a link event) and do something other than the default. That iterator model is also the reason it's fast: no allocation-heavy tree construction, single pass, one of the fastest CommonMark parsers in any language by the benchmarks the project itself publishes and that third parties have reproduced.

The cost is that pulldown-cmark deliberately stays close to spec compliance and doesn't wander into non-standard extensions. Wikilinks, if added later, would need a custom pre-pass or a fork of the event stream — doable, since the event model is designed to be intercepted, but it's your code to write, not a flag to flip.

### Rendering in Rust: comrak

comrak is a port of GitHub's own `cmark-gfm` reference implementation, which makes it the most GFM-faithful option almost by construction — if GitHub's preview renders a document a certain way, comrak is the Rust library most likely to match it exactly. It's at least as actively maintained as pulldown-cmark by the numbers: pushed 2026-09-14, latest release v0.55.0 on 2026-09-06, only 16 open issues, a fast-moving and well-triaged project. It builds a full AST (not a lazy event stream), which is heavier per parse but much easier to post-process — walking a tree to rewrite link targets or inject a table of contents is simpler than reconstructing that logic from an event iterator. It also ships broader extension coverage out of the box than pulldown-cmark: footnotes, description lists, superscript, and (relevant later) it has an existing syntax-highlighting hook point that plugs into syntect directly, which is a real convenience if syntect is the highlighting choice below.

The cost is exactly the flip side of its convenience: an AST means an allocation per node on every keystroke's re-parse, and for a resident app that re-parses on every debounce tick over potentially many open tabs, that's a real (if probably still small) cost pulldown-cmark doesn't pay. It's also a heavier dependency tree.

### Rendering in the frontend: markdown-it

markdown-it is the JS incumbent — a plugin-based CommonMark+GFM parser (with GFM tables/strikethrough/tasklists via community plugins, not built in) that's extremely well trodden: 15.0.2 on npm as of this check, pushed to GitHub 2026-09-12, only 8 open issues, 16M+ weekly downloads. Its plugin architecture is the best answer to the "extension points for wikilinks/Mermaid/math later" requirement of any option considered here — there are already mature, maintained plugins for footnotes, task lists, and (via `markdown-it-katex`-style plugins) math, and writing a wikilinks plugin is a well-worn pattern with prior art to copy.

The catch for medd specifically is D-2's architecture: rendering in the frontend means the *source* has to cross the IPC bridge into the WebView (or already live there, if the editor buffer is frontend-resident, which it will be regardless of parser choice — see [q9](q9-editor-component.md)), and if any other part of the system needs the rendered HTML on the Rust side — for logging, for a later export feature — it has to come back the other way. In practice that's not a real problem: the editor buffer already lives in the WebView because that's where CodeMirror runs, so the "IPC cost" argument that superficially favours Rust-side rendering mostly evaporates once you notice the source text never has to leave the frontend to be rendered there.

### Rendering in the frontend: remark/unified or micromark directly

The unified/remark ecosystem (all maintained by the same author, wooorm, who also wrote markdown-rs) is the more "correct" choice on paper — micromark is a from-scratch CommonMark tokenizer with an unusually rigorous compliance record, and remark's plugin ecosystem (remark-gfm, remark-math, remark-wiki-link) is the deepest available anywhere for exactly the deferred features medd will eventually want. Checked live: micromark pushed 2026-09-11 (14 open issues), remark pushed 2026-09-01 (11 open issues) — both healthy.

The honest cost is architectural weight for no corresponding benefit here: unified's whole value proposition is a plugin pipeline operating on ASTs (mdast) that multiple downstream consumers (React renderers, static site generators, linters) share. medd has exactly one consumer of the parsed document — its own preview pane — so paying unified's abstraction cost buys nothing markdown-it's simpler plugin model doesn't already cover for this app's needs.

### Syntax highlighting: syntect/two-face (Rust) vs shiki/highlight.js/Prism (JS)

syntect (Sublime Text grammar-based, TextMate-grammar compatible) is the standard Rust choice, and it is maintained but not fast-moving: last GitHub push 2026-04-28, but its last *tagged release* was v5.3.0 back in September 2025 — a year-old release with recent-ish repo activity on top, and 136 open issues on a project that's clearly past its main development phase and now in upkeep mode. That's a legitimate concern for a project this central, but it's a stable, well-understood one — syntect is what `bat`, `delta`, and a large share of Rust terminal tooling already ship, so its rough edges are well documented. two-face (the maintained fork of the old syntax-set-bundling crate, at `CosmicHorrorDev/two-face`, pushed 2026-01-01) solves syntect's biggest practical annoyance, which is that its default syntax/theme sets are thin and loading a full Sublime `.tmTheme`/`.sublime-syntax` set at runtime is slow; two-face ships a pre-compiled binary blob of syntaxes and themes that loads near-instantly. The real cost of the Rust-side highlighting path is memory: syntect's compiled syntax definitions for a reasonably full language set run to several megabytes resident, which is a permanent tax on an always-open, idle-most-of-the-time process (N-1) — not huge in absolute terms on a modern Mac, but it's paid once at startup and never released, which is exactly the shape of cost N-1 is trying to keep an eye on.

On the JS side, shiki (TextMate grammars via an embedded Oniguruma/WASM engine, the same approach VS Code uses) gives the most accurate, VS-Code-quality highlighting available anywhere, actively maintained (v4.4.3, released 2026-08-10, pushed 2026-09-11), but it is the heaviest of the three JS options — full grammar files per language, loaded lazily or bundled, with an npm unpacked size around 15MB if every grammar ships. highlight.js is lighter conceptually (regex-based, not TextMate grammars) and ships a genuinely mature, if not currently fast-moving, project (last real release 11.12.0, 2026-08-12, actively pushed) — good-enough highlighting for the mainstream languages a personal notes/docs workspace will actually contain (bash, rust, python, json, yaml, javascript), materially simpler to integrate than shiki, and it can be configured to bundle only the languages medd expects rather than the full language set. Prism, despite still receiving repo pushes (2026-09-14) is functionally stale — its last real tagged release was v1.30.0 in March 2025, eighteen months ago, and its open-issue count (488) reflects a project not being actively triaged; it is not a credible choice for new work in 2026 regardless of its famously small core bundle.

Whichever side does highlighting, it should run in the frontend if rendering runs in the frontend: shipping a fully syntax-highlighted HTML blob for every fenced code block over IPC on every keystroke, when the WebView could just as easily do it locally with no IPC involved, is work with no benefit.

### Sanitisation: ammonia vs DOMPurify

If HTML gets sanitised on the Rust side, ammonia is the only serious option: whitelist-based, built on html5ever (the same HTML5 parser Firefox's Servo project produced), actively maintained (pushed 2026-09-14, v4.1.4 released 2026-07-22). If sanitisation happens in the frontend instead, DOMPurify is the de facto standard everywhere on the web — extremely actively maintained (pushed 2026-09-14, v3.4.14, 22M+ weekly downloads, zero open issues at time of check, which for a project this size means an unusually well-run triage process, not an absence of users). Both are excellent; the choice here just follows wherever rendering ends up happening, since sanitising in one process and rendering in the other only adds a hop for no security benefit — the sanitiser needs to run on the HTML immediately before it's inserted into the DOM that will display it.

## Recommendation

**Render Markdown to HTML in the frontend, using markdown-it with the standard GFM plugin set (markdown-it plugins for tables, tasklists, strikethrough, footnotes), highlight with highlight.js configured to a curated language subset, and sanitise with DOMPurify immediately before inserting into the DOM.**

The deciding factor is D-2 and D-3 together: the editable buffer already has to live in the WebView, because that's where the source-pane editor component runs and where keystrokes originate (see [q9-editor-component.md](q9-editor-component.md)). Given that, rendering in the same process means the render pipeline never touches Tauri IPC at all on the hot path — no `invoke` call, no JSON-serialised HTML crossing a bridge, on every keystroke. That directly serves N-3 better than any Rust-side option can, because the fastest IPC call is the one that doesn't happen. It also means the "does the sanitiser and the renderer agree on what's safe" question collapses to a single process's problem, and it gives medd the deepest, most battle-tested plugin ecosystem for exactly the deferred features (wikilinks, math, eventually Mermaid as a fenced-code-language special case) that the roadmap already commits to wanting later.

Rust's job in this pipeline is not rendering — it's file I/O, autosave, file-change watching, and the workspace/tab state machine, which is where a Rust core actually pays for itself in this architecture. Markdown parsing on the Rust side would only earn its keep if the app needed to do something with rendered or parsed Markdown *outside* the WebView — batch-processing many files headlessly, say, for a future full-text search index (Q-9 in open-questions.md, explicitly deferred) — and nothing in v0.1's scope needs that.

## Trade-off accepted

markdown-it's own CommonMark/GFM compliance is looser at the edges than comrak's (which mirrors GitHub's reference implementation exactly) or pulldown-cmark's (which tracks the CommonMark spec test suite closely) — corner cases in nested emphasis or malformed table syntax may render very slightly differently than github.com would render the same file. For a personal notes and documentation workspace, not a GitHub-preview clone, that gap is very unlikely to be visible in practice, and it buys a materially simpler architecture with no IPC involved in the render path and the best available extension story for the roadmap's deferred features. If pixel-perfect GitHub-preview fidelity ever becomes a stated requirement, that's the point to revisit comrak specifically — not pulldown-cmark, since comrak's whole reason to exist is being the closest AST-based match to cmark-gfm.

## Risks / unknowns

- **Full re-parse on every keystroke.** markdown-it re-parses the whole document each debounce tick rather than incrementally; for typical notes/docs-length files (a few KB to tens of KB) this is not measurably slow in any modern JS engine, but Q-4 (large-document behaviour) is explicitly open, and the answer to "does a 5MB file stay responsive" depends on this choice more than any other. This doc doesn't resolve Q-4; whoever does should re-check markdown-it's re-parse cost against a real large-file benchmark before committing to a debounce strategy for oversized documents.
- **highlight.js's regex-based approach can mis-highlight ambiguous syntax** that a TextMate-grammar engine like shiki gets right; this is a real but minor quality gap, acceptable for v1 and revisitable if it visibly bothers the user in daily use — shiki is a drop-in-shaped upgrade later since both output HTML with CSS classes/inline styles that can be swapped independently of the Markdown parser.
- **DOMPurify's necessity depends on how much raw HTML the user's own Markdown files actually contain.** Since this is a local-first, single-user tool with no untrusted content ever entering the pipeline (N-6, no network input), the sanitisation step is defense against the user's own copy-pasted HTML snippets misbehaving, not against an attacker — worth keeping for correctness (stray `<script>` tags shouldn't execute in the preview) but not a load-bearing security boundary the way it would be in a multi-user product.
- **markdown-it's plugin ecosystem quality for GFM tables/tasklists/footnotes specifically** wasn't independently verified plugin-by-plugin in this pass (e.g. `markdown-it-footnote`, `markdown-it-task-lists`) — they're widely used and stable in practice, but whoever wires this up should sanity-check maintenance status on the specific plugins chosen, since plugin maintenance quality varies more than the core library's.
